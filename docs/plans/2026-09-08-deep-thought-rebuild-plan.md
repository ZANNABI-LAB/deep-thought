### 목표는 둘이고, 중단 조건이 다르다

**이 구분이 이 기획서에서 가장 중요하다.**

| 프로젝트 | 위상 | 중단 조건 |
|---|---|---|
| **블로그 전면 재구축** (D·A) | **숙원 사업. 그 자체로 목적** | **없음. 완주한다** |
| **SEO 색인 회복 + AdSense 승인** | **명시적 목표** | **없음. 완주한다** |
| **굿즈 + 커머스 백엔드** (C·B) | 브랜딩 수단 | **조건부.** 독자 지표 게이트 미달 시 보류 (§6) |

재구축은 굿즈의 선행 조건이 아니다. 굿즈가 접혀도 재구축은 계속된다. 반대로 재구축이 끝나도 독자 지표가 안 나오면 굿즈는 착수하지 않는다.

굿즈의 1차 목적은 수익이 아니라 **브랜딩과 독자 관계 강화**이며, 수익 기준은 **"손해만 안 보면 성공"** 이다. 이 전제가 예약주문·소량 발주·보수적 환불 정책의 근거다.

### 실행 주체: **전부 직접** (확정)

v0.4는 누가 디자인하는지를 적지 않았고, fable이 이를 "가장 검증되지 않은 가정"으로 지적했다. 실물 자산을 확인한 결과 **난이도 평가 자체가 과대했다.**

**근거 — 마스코트는 순수 도트 아트다**
```
mascot-full.png : 1254×1254, 2-bit colormap, 고유색 3개
mascot-96.png   :   96×96,  2-bit colormap, 고유색 3개
```

이 사실이 두 리스크의 난이도를 크게 낮춘다.
- **R13(벡터화)** — 도트 아트는 픽셀 하나 = 사각형 하나다. 그리드 → SVG 변환은 **기계적**이고 스크립트로 처리된다. 무한 확대해도 깨지지 않는다
- **R1(CMYK 검증)** — 검증할 색이 **3개**뿐이다. 수백 색 그라데이션을 맞추는 작업이 아니다

**산출물별 난이도**

| 산출물 | 난이도 | 비고 |
|---|---|---|
| 컨셉 정의 | 낮음 | 본인이 브랜드를 가장 잘 안다 |
| 화면용 팔레트 | 낮음 | phase4~6에서 이미 수행 |
| 디자인 토큰 / UI | 낮음 | 기존 CSS 변수 구조가 잘 짜여 있다 |
| 로고·심볼 벡터 | 낮음 | 도트 그리드 → SVG |
| 인쇄용 팔레트(CMYK) | 중간 | 색 3개. 실물 교정은 인쇄소가 수행 |
| 단색 축소판 | 중간 | 3색 → 1색 단순화 |
| **마스코트 새 그림체** | **높음** | 유일하게 그림 실력이 필요한 부분 |

**도트 컨셉 유지 결정이 D의 난이도를 낮춰준다.** 도트는 픽셀 에디터(Aseprite 등)로 격자에 색을 찍는 작업이라 일반 일러스트보다 진입 장벽이 훨씬 낮다.

**안전장치**: 8주를 초과하면 마스코트 드로잉만 외주로 전환한다(§9).

### 설계 조건: 인쇄 가능성을 처음부터 넣는다

- [ ] **색 수 제한** — 주조색 1~2도
- [ ] **CMYK 색역 내 팔레트** — 확정 전 검증. 화면용/인쇄용 2벌
- [ ] **벡터 로고·마스코트** — 900×400mm 확대를 견딜 것 (R13)
- [ ] **단색 축소판** — 1도 실크스크린용
- [ ] **큰 면적에서 성립하는 패턴** — 장패드는 화면과 여백 설계가 다르다
- [ ] **타이포그래피 — 굿즈 인쇄 포함 상업 이용 라이선스**

도트/터미널 계열 유지. 이유: 인쇄 친화적(색 수 적음, 그라데이션 없음), 마스코트와 자연스럽게 맞음, 기술 블로그 정체성. phase4~6 시안을 참고하되 그대로 쓰지 않는다.

### A1-b. Tech 축 재설계 — 양산에서 견해로 🔴

**문제**: Search Console에서 **자동 색인이 되지 않고 있다**(사용자 확인). 기술적 원인은 아니다 — `robots.ts`는 전체 허용에 sitemap을 선언하고 있고, canonical·JSON-LD·metadataBase가 모두 갖춰져 있다.

**진단** (증거 기반 추론):

| 요인 | 내용 |
|---|---|
| 주제 경쟁도 | CQRS·DNS·CORS 등 **기술 면접 단골 주제**. 같은 주제의 고신뢰 도메인 글이 이미 수천 개 |
| 패턴 획일성 | 132편이 동일 파이프라인·동일 템플릿(`## X란? → ## 핵심 개념 → ### 1.`) |
| 정책 저촉 소지 | 구글 **대규모 콘텐츠 남용(scaled content abuse)** 정책은 AI 여부가 아니라 *순위 목적의 대량 생산*을 본다 |
| 파생 콘텐츠 | 매일메일 원본 질문에 답한 구조라 파생물로 보일 여지 |

본문 길이는 문제가 아니다 — 중앙값 3,416자, 코드 예제 포함. **얇은 콘텐츠가 아니라 차별성 없는 콘텐츠다.**

**따라서 v0.6의 전제 "Tech(자동 생성) = 유입 담당 — 그대로 둔다"는 폐기한다.** 유입을 만들지 못하고 있고, 같은 패턴으로 170편을 더 부으면 **사이트 전체 평가가 더 나빠질 수 있다.**

**아카이브 중복 실측**: pending 170편 중 기존 132편과 주제가 겹치는 것은 **2편뿐**이다(함수형 프로그래밍, TCP 3-way handshake). 재생성의 명분은 중복 제거가 아니라 **견해 주입**이다. pending은 카테고리가 더 세분화되어 있어(`JavaScript 기초와 런타임` 19, `Persistence와 데이터베이스` 15 …) 롱테일 재료로는 오히려 낫다.

**새 파이프라인 — 사람 개입을 발행 게이트로**

> ⚠️ **핵심**: "내 견해"를 AI가 대신 쓰면 아무것도 바뀌지 않는다. 구글과 AdSense가 보는 것은 *AI가 썼는가*가 아니라 **이 사이트에만 있는 정보인가**이다. AI가 생성한 견해는 그 어디에도 없는 정보가 아니다.

```
1. AI가 기술 설명 초안 생성           (기존과 동일)
2. AI가 '견해가 필요한 지점' 질문 3개 생성
     · 실무에서 언제 써봤나
     · 어떤 함정을 겪었나
     · 통념과 다르게 생각하는 지점은
3. ★ 사람이 답을 채운다 — 발행 게이트
4. 미작성 시 draft 유지. 자동 발행 없음
```

- [ ] 파이프라인을 반자동(human-in-the-loop)으로 개조
- [ ] **발행 속도 하향 수용** — 하루 3편 → 주 2~3편. 양산이 문제였으므로 이는 비용이 아니라 목적이다
- [ ] 자동 발행 워크플로우 제거 또는 draft 생성까지만 수행하도록 변경

**기존 132편 처리 — 전량 개선은 비현실적**

| 대상 | 처리 |
|---|---|
| 신규 발행분 | **처음부터 견해 포함. 예외 없음** |
| 기존 132편 중 노출 상위 | Search Console 데이터 확보 후 상위부터 점진 개선. **slug 유지** |
| 나머지 | 일단 유지. 여력 생기면 처리 |

- [ ] **slug를 바꾸지 않는다.** URL 고정 + 내용 개선이면 SEO 손실 없이 재평가를 받는다. 삭제·URL 변경은 누적분까지 잃는다
- [ ] 삭제는 하지 않는다 — 장패드 서사("내가 쓴 글이 깔린 책상")의 근거이기도 하다

## 5. SEO 전략

### 성격: 새로 만드는 것이 아니라 잃지 않는 것

레거시 저장소에는 SEO가 **이미 상당 수준으로 구현되어 있다.** 재구축의 과제는 신규 구축이 아니라 **무손실 이관**이다.

| 이미 구현된 것 | 위치 |
|---|---|
| 동적 sitemap (포스트·로그 자동 수집, lastModified·priority) | `src/app/sitemap.ts` |
| robots | `src/app/robots.ts` |
| RSS 피드 | `src/app/feed.xml/route.ts` |
| 동적 OG 이미지 (Satori) | `src/app/api/og/route.tsx` |
| `metadataBase` (`https://deep-thought.space`) | `src/app/layout.tsx` |
| canonical | 각 페이지 `alternates.canonical` |
| 파비콘 | `src/app/icon.svg` (phase6는 `icon.png` + `apple-icon.png`) |
| **구조화 데이터(JSON-LD)** | `WebSite`, `Person` (layout·profile), `Article` + `author`/`publisher` (tech·log 상세) |

**이것들을 하나라도 빠뜨리면 재구축은 SEO 순손실이다.** 신규 저장소에서 처음부터 짜지 말고 **이관 후 개선**한다.

### 실측 — 2026-09-09 Search Console

| 항목 | 값 |
|---|---|
| **색인된 페이지** | **5개** (3개월간 변동 없음) |
| 색인된 URL | `/` · `/profile` · `/portfolio` · `/log/2026-03-07-first-log` · `/tech/authentication-authorization-security` |
| Tech 포스트 색인율 | **1 / 132 = 0.8%** |
| Log 색인율 | 1 / 1 = 100% (표본 1, 통계적 의미 없음) |

**R21이 추정에서 확정으로 바뀌었다.** 기술적 차단은 없으므로(robots 전체 허용, sitemap 선언됨) 남는 설명은 **콘텐츠 차별성 부재**뿐이다.

**이에 따른 결정:**
- **URL 동결 해제.** 131편이 미색인이므로 URL 변경의 SEO 손실은 사실상 0이다
- **단 색인된 5개 URL은 유지한다.** 유지 비용이 0이고 손실만 막는다
- **평면 구조 권장** — 카테고리를 경로에 넣으면 카테고리 정리 시 URL이 깨진다. 날짜 삽입은 콘텐츠 노후 신호
- 게이트 기준선: 색인 5개, 유입 사실상 0. **바닥에서 시작한다는 것이 확인됐다**

### 재구축 고유의 SEO 리스크

| 위험 | 왜 발생하나 | 대응 |
|---|---|---|
| **URL 변경** | ~~구조를 바꾸고 싶은 유혹~~ | **완화됨** — 색인 5개뿐이라 손실이 없다. 그 5개만 유지 |
| **도메인 이전 공백** | Vercel 프로젝트 전환 중 DNS 미연결 구간 | 신규 배포를 먼저 완성 → 도메인만 스위치. **다운타임 0을 목표** |
| **이관 누락** | sitemap·JSON-LD는 눈에 안 보여 빠뜨리기 쉽다 | 위 인벤토리 표를 **이관 체크리스트로 사용** |
| **인덱싱 리셋 착각** | 저장소가 바뀌면 SEO도 리셋된다는 오해 | 색인은 **도메인 기준**이다. 저장소는 무관 |
| **slug 정규화 유혹** | 카테고리 정리(A2) 중 slug까지 손대는 것 | **카테고리는 정리하되 slug는 건드리지 않는다** |

### 이관 체크리스트

- [ ] sitemap / robots / feed.xml 이관 후 **실제 응답 검증**
- [ ] JSON-LD 4종 이관 — 리치 결과 테스트로 검증
- [ ] `metadataBase`, canonical 전 페이지 확인
- [ ] OG 이미지 라우트 이관 (`next/og`는 Next.js 잔류 — §7)
- [ ] 파비콘·apple-icon
- [ ] **색인된 5개 URL 유지 확인** (나머지는 재설계 자유)
- [ ] 도메인 스위치 후 Search Console **URL 검사 + 사이트맵 재제출**
- [ ] 404 급증 모니터링 (전환 후 2주)

### 신규로 필요한 것

**A(블로그) 단계**
- [ ] `BreadcrumbList` 구조화 데이터 — 카테고리 계층이 정리되면(A2) 의미가 생긴다
- [ ] 카테고리·태그 목록 페이지의 색인 정책 결정 (얇은 페이지 대량 생성 주의)
- [ ] Core Web Vitals 점검 — D3 force simulation이 도는 메인은 **LCP·INP 위험 구간**이다
- [ ] 자동 생성 글의 품질 관리 — 132편이 유사 구조라 **얇은 콘텐츠로 평가받을 위험**이 있다 (R21)

**C(스토어) 단계 — 게이트 통과 시**
- [ ] `Product` / `Offer` 구조화 데이터 (가격·재고·배송)
- [ ] 상품 페이지 canonical, OG 이미지
- [ ] 예약주문 페이지의 색인 정책 — **판매 종료 후 방치되면 마이너스**다
- [ ] 법정 고지 페이지는 `noindex` 검토

### 측정 — Search Console이 R7의 해답이 될 수 있다 🔴

**중요**: Supabase 삭제로 조회수·방문 통계는 소실됐지만, **Google Search Console 데이터는 그와 무관하게 남아 있다.** 도메인이 등록되어 있다면 최대 16개월치 검색 노출·클릭·질의 데이터가 보존된다.

이것이 **R7(독자 존재 미검증)을 부분적으로 해소**한다. 지금까지 "트래픽을 알 방법이 없다"고 전제했으나 **틀렸을 수 있다.**

- [ ] **Search Console 등록 여부 확인 — 최우선 조사 항목**
- [ ] 등록되어 있다면: 지난 16개월 노출·클릭·상위 질의·유입 페이지 확보
- [ ] 미등록이라면 **지금 즉시 등록** — 데이터는 등록 시점부터 쌓인다. 하루라도 빠른 게 낫다
- [ ] 이 데이터를 **독자 지표 게이트(§6)의 기준선**으로 사용

### AdSense — 목표로 채택

`ads.txt`에 퍼블리셔 ID(`pub-6873591317343081`)가 이미 존재한다. 계정은 있다.

**승인 기준은 "고유하고 가치 있는 콘텐츠"이며, 이는 색인 문제와 뿌리가 같다.** 현 상태로 재신청하면 거절 사유가 그대로 반복된다.

- [ ] **선행 조건: A1-b(견해 주입) 진행 + Log 축적.** 이것 없이 재신청하지 않는다
- [ ] 심사 전 필수 페이지 정비 — 개인정보처리방침, 문의 경로, 소개(Profile)
- [ ] 광고 배치 정책 결정 — 레거시는 Tech 사이드바(`ad-unit.tsx`, `NEXT_PUBLIC_ADSENSE_ENABLED`). **브랜딩이 1차 목적이므로 과밀 배치는 역효과**
- [ ] 승인 후에도 굿즈 스토어 페이지에는 광고를 넣지 않는다 (구매 흐름 방해)

> **SEO·AdSense·A3(자기 목소리)·굿즈 브랜딩은 전부 같은 해법을 가리킨다** — 고유 경험 콘텐츠. 따로 하는 일이 아니다. "CQRS 패턴"은 수천 명이 썼지만 "1비트 도트 마스코트를 900×400 장패드로 인쇄했더니 생긴 일"은 아무도 쓰지 않았다.

### 원칙

> **SEO는 A의 하위 작업이 아니라 A의 완료 조건이다.**
> "배포됨"이라는 DoD(§9)에 "SEO 이관 검증 통과"를 포함한다.

## 6. 독자 지표 게이트 🔴

**B·C 착수 조건.** D·A와 달리 이 둘은 무조건 진행하지 않는다.

### 왜 필요한가

독자의 존재가 **한 번도 검증된 적이 없다.** 분석 데이터는 Supabase와 함께 소실됐고, 132편 전부 AI 생성이며, 5개월간 발행이 없었다. "관점을 사는 물건"을 파는데 관점 있는 글이 0편인 상태에서 스토어·백엔드·생성기를 짓는 것은 순서가 뒤집힌 것이다.

### 게이트 설계

- [ ] **A 완료 후 3개월간 Log 주 1회 발행**
- [ ] 그 기간의 지표로 판단 — 유입, 재방문, 구독(RSS·뉴스레터), 반응(댓글·언급)
- [ ] **구체적 임계값은 A 완료 시점에 확정** (지금은 기준선 데이터가 없어 숫자를 정할 수 없다)
- [ ] 게이트 미달 시 → **C 보류.** D·A는 그대로 완주

> 예약주문 최소 수량(업체 MOQ)은 **손실 방어 장치**이지 수요 검증 게이트가 아니다. 둘을 혼동하지 않는다.

| 챗봇 RAG + SSE | Spring — **C2 이후** |
| **주문 · 결제 · 발주** | **Spring — B의 진짜 이유** |

> **정직한 평가**: 조회수·통계만 놓고 보면 백엔드 분리는 과잉 설계다. 정당화하는 것은 커머스 도메인과 포트폴리오 목적이다.
>
> **추가 고려**: 백엔드 포트폴리오 목적의 별도 프로젝트(SwapVe)가 이미 있다. 1인의 시간을 두 포트폴리오 프로젝트가 나눠 갖는다는 점을 인지하고 착수한다.

### 데이터: Neon (Postgres + pgvector)

Supabase의 가치는 *백엔드 없이 프론트가 DB를 직접 쓰게 해주는 것*(자동 REST API, Auth, RLS)이다. Spring이 그 층을 대체하므로 남는 건 관리형 Postgres 한 대다. 무료 티어의 자동 pause는 복구가 수동이라 방치 리스크를 만든다.

**v0.4 정정**: "pgvector 되는 관리형 Postgres가 의외로 적다"는 **과장이었다.** 대부분의 관리형 Postgres가 지원한다. Neon을 택하는 실제 이유는 **자동 pause 후 자동 복구(수동 개입 불필요)** 와 무료 티어다.

- [ ] Flyway 도입
- [ ] 스키마 신규 설계 — **이관할 데이터 없음. 깨끗한 시작**

### 배포 / 운영

**v0.4 정정 — 콜드스타트 논리가 틀렸다.**
- 조회수 기록은 **fire-and-forget 비동기**로 짜면 페이지 렌더를 막지 않는다. 레거시 `api/views/route.ts`도 실패 시 `viewCount: 0`을 반환하는 비차단 설계다
- **always-on JVM + scale-to-zero Neon은 모순**이다. 트래픽이 적으면 DB가 자므로 첫 쿼리는 어차피 기다린다
- → **상시 가동 유료 인스턴스는 근거 부족.** B 착수 시 실측으로 재판단한다

- [ ] 호스팅 결정 및 월 비용 상한
- [ ] CORS, 환경변수 이원화, 시크릿 관리
- [ ] CI/CD, 로컬 개발 환경(docker compose)
- [ ] **게스트 주문 + 주문번호 조회.** 회원 시스템은 개인정보 부담만 늘린다
